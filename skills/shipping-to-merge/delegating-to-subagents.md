# Delegating to Subagents (if you fan the build out)

You MAY hand the **build** (steps 1–4) to subagents — e.g. one repo per agent in parallel. You MUST NOT hand off the **merge gate** (steps 5–7): the orchestrator owns babysitting, final re-verify, and merge, and merges only after **independently** confirming the subagent's claims. A subagent's final message is a *claim*, not evidence. "Done, green, pushed" has been false before — verify it yourself.

### What every build subagent prompt MUST contain (no exceptions)
Copy these requirements into the prompt verbatim — a subagent only does what its prompt says, so an omitted requirement is a skipped gate:
1. **Exact worktree command + fixed location** `<repo>/.claude/worktrees/<branch>` off `origin/<default-branch>`; detect the default branch (NOT always `master`); confirm `git rev-parse --show-toplevel` + `git branch --show-current` before editing. Work ONLY in that worktree.
2. **The repo's COMPLETE pre-PR gate command(s)**, run in full (never a scoped subset) — lint + types + the WHOLE test suite (`scripts/verify.sh` or the documented equivalent; FE = full `lint` + `typecheck` + the test runner, e.g. vitest). Fix everything; open the PR only when fully green.
3. **Behavioral/visual verification when the change has runtime behavior** (UI, endpoint, CLI) — run the app and observe the change, not just unit tests (REQUIRED BACKGROUND: the `verify` / `run` skills). If it genuinely cannot be run, the subagent must say so explicitly so the orchestrator does it.
4. **Conventional Commits; never `--no-verify`; merge-commit repo (no squash); do NOT merge** — stop at "PR opened".
5. **Base-not-stale check** (`git diff --shortstat origin/<default>..HEAD`); merge-in default + re-run the gate if it moved.
6. **Code review before the PR (step 3.5)**: after the gate is green and committed, dispatch a reviewer (`opus-reviewer` for high-risk changes, `sonnet-reviewer` for routine ones — see Model routing) per `superpowers:requesting-code-review` with `{DESCRIPTION}` + `{PLAN_OR_REQUIREMENTS}` (the real plan text) + `{BASE_SHA}` + `{HEAD_SHA}`, plus "trace what this change breaks elsewhere". No threat-list. Fix Critical/Important, re-run the gate, THEN push. Report the findings and what was fixed vs deferred. **If a spec/plan/ADR governs this change, paste its governing text/excerpt into the reviewer prompt and require the reviewer to verify the code AGAINST each requirement + acceptance criterion (met? invariant violated? silent deviation?) — not just review the diff for local correctness — and to say so if the spec/plan itself is wrong. A clean diff that fails a spec requirement is a FAIL.**
7. **Resource discipline (parallel agents share ONE developer machine)**: while building, run targeted tests + the repo's SCOPED/fast gate; run the COMPLETE gate (requirement 2) exactly ONCE — immediately before opening/updating the PR, and again only after merging a default-branch change that touched code. On a red, re-run only the failing test first; never loop the full gate. Docs-only diffs need no local full test suite (doc gates + hosted CI). Never bypass the repo's own CPU/slot budget (no raw `pytest -n auto` / unbounded vitest / Gradle daemons — use `--no-daemon`). No stress/load tests unless the task asks. A failure with zero assertion failures under high `uptime` load is contention — re-run that test, never loosen it. Follow the repo's own resource rules (e.g. CLAUDE.md) where they exist. **The machine is the user's desktop and must stay responsive:** prefix EVERY heavy command (test runners, full gates, builds, migrations, installs) with `nice -n 19 ionice -c 3`; cap test parallelism explicitly (pytest `-n 3` max, `--maxWorkers=3`, Gradle `--max-workers=3`) — never `-n <nproc>`/`-n auto` in a direct run, because a direct runner bypasses the repo gate's budget (observed: a raw `pytest -n 12` pinned all 12 cores and lagged the UI). Never search the whole filesystem (`find /`, `bfs /`, `fd . /`) — search the repo, and `~/.cache` with `-maxdepth` if you must; if a fixture/suite is not in the repo, say so instead of hunting.
8. **Private scratch paths**: temp files (PR body, commit message) go under a per-branch subdirectory of the scratchpad, never a shared name like `pr.md`; publish with `&&` after the write succeeds (observed: a builder published another builder's overwritten `pr.md` as its PR body).
9. **Evidence-with-output report**: the PR number+URL, the **verbatim final gate output** proving green, `git rev-parse HEAD` AND `@{u}` (proving the pushed tip), the file list, the review findings + triage, and any deviation/skip with rationale. "If the gate can't go green, STOP and report the failing output — do not open the PR."

### Model routing (cost per COMPLETED task, not per token) — operator default since 2026-09-29
Only two tiers, both at **medium** effort: **Opus 5.5** (the orchestrator — you — plus escalations) and **Sonnet 5.5** (the default workforce). Global agent types exist for this (`~/.claude/agents/`): `sonnet-worker`, `opus-worker`, `sonnet-reviewer`, `opus-reviewer`. Dispatch with `subagent_type` (it carries model + effort); **never dispatch with a bare `model:` override** — it cannot set effort and bypasses routing entirely (measured 2026-09-29→10-01: 12 of 33 dispatches were untyped `model: "opus"`, including pure docs recording).
- **Route by judgment required, never by size.** Huge-but-mechanical → Sonnet; tiny-but-subtle → Opus.
- **Opus decides, Sonnet builds** (operator, 2026-10-01). Measured 2026-09-29→10-01 on one repo: 16 of 19 dispatches went to Opus types, Opus subagents used ~96% of subagent tokens, and single opus-workers ran 300–800 calls with context reaching 400–613k. "High-risk" covered almost everything, so the default worker almost never ran.
- **`sonnet-worker` (default — including high-risk areas once the design is settled):** well-scoped implementation in a bounded set of files, tests, mechanical refactors/migrations, dependency/version bumps, docs/ledger/plan recording, log reading, repo search, focused fixes with an obvious root cause. For security/privacy (auth, RBAC, tenant isolation/RLS, audit, crypto/trust material, retention/erasure), risky DB migrations and whatever the PROJECT declares high-risk: YOU (the Opus orchestrator) settle the design first — the approach, the invariants that must hold, the files, the tests that prove it, what must not change — and put it in the brief; then `sonnet-worker` builds and `opus-reviewer` reviews before merge. Do not route to Opus merely because a task touches a high-risk subsystem; route to Opus when it needs unresolved judgment. If settling the design needs real investigation, do it yourself or dispatch `opus-worker` for a **design-only** pass that returns a brief, not code.
- **`haiku-scout` (cheap read-only lookups):** one bounded question with a short, evidence-backed answer — locate a symbol or its call sites, extract the failing tests + first error from a CI/gate log, list matching ledger rows, summarise long output. Never for correctness, security, design or review verdicts (Haiku may COLLECT evidence in a high-risk area; Sonnet/Opus judge it). Prefer a direct `rg`/`git`/`gh` command when that alone answers it. Never force Haiku globally (`CLAUDE_CODE_SUBAGENT_MODEL_FORCE`), never a Haiku reviewer.
- **`opus-worker`:** judgment that cannot be settled before building starts — architecture/design choices, ambiguous or conflicting requirements, cross-cutting changes whose shape emerges while working, hard multi-system debugging with an unknown root cause, and any task a Sonnet worker failed or needed significant correction on. Not "anything near a high-risk file".
- **Escalate, don't crank effort:** if a Sonnet worker fails, loops on the same error twice, or needs significant correction, re-dispatch the task (with what was learned) to `opus-worker`. Never raise Sonnet's effort as the fix for a reasoning problem.
- **Reviewers follow the CONSEQUENCE of the change, not its path or its worker:** `opus-reviewer` for any behavior change in a high-risk area (security/privacy, data lifecycle, migrations, the project's declared high-risk domains — always for spec/ADR-governed invariants) **and whenever the risk classification is unclear**; `sonnet-reviewer` for clearly routine diffs, including a provably behavior-neutral edit inside a high-risk file (typo, comment, rename the gate fully covers) — say why in the dispatch note. The review gate is where bugs are caught — do not downgrade it to save tokens on high-risk code.
- **You (Opus) always keep the merge gate:** independent re-verification of every worker's claims is unchanged by which model built it.
- **Verify routing actually happened** (subagent model bugs exist: overrides silently ignored, UI showing the parent's model): don't trust the agent label — check the effective model (`/tasks`, the transcript, `effective_model` in the tool result where exposed) when testing the setup or when a worker's behaviour looks like the wrong tier.
- **No Sonnet-high rung by default** (operator chose medium-only, 2026-09-29): escalate by MODEL. Revisit only with data showing Sonnet-medium failures that did not need Opus judgment.
- Put the chosen type and one-line reason in your dispatch note, so the cost/correction pattern can be reviewed later.

### Context and dispatch hygiene (most of the cost is context, not output)
- **Don't spawn for trivia.** A lookup or edit you can do in a few tool calls stays in the main session; an agent is for independent work, parallelism, context isolation or review.
- **One focused task per agent, one PR per agent.** Give the brief a scope list, an explicit "do not touch", the verify commands and the return format. Smaller boundaries mean less wandering.
- **Context threshold (~200k, a practical hand-off point, not a model limit):** once a worker has finished its useful investigation or passes ~200k, it should finish its current step, commit/push WIP, and report a short handoff (done / remaining / traps) unless it is genuinely about to finish. Continue with a FRESH agent and that handoff. Resuming a stalled agent on the SAME task is fine; resuming a huge-context agent for a NEW task is not.
- **Concise reports:** the report is the evidence list in requirement 9 — PR, verbatim gate verdict lines, `HEAD`/`@{u}`, files, review triage, deviations. No narrative.
- **Reviewers get the diff and the governing spec text**, not the build history.
- **Orchestrator:** `/compact` at milestones (dispatch done → babysitting; merged → next wave), `/clear` or a new session when the topic changes. Persist state in memory/the wave log first so nothing is lost.
- **Measure, don't guess:** `python3 ~/.claude/scripts/subagent-usage.py [project-dir] [--since YYYY-MM-DD]` prints dispatches by type and subagent tokens by model. Check it after a wave; if Opus share is high, the routing above is being skipped.

### Orchestrator load rules (before dispatching)
- **Before each launch, check `uptime` and `coredumpctl list --since today | tail -3`.** If load is already above `nproc` from something else (a crash-looping daemon, a render job), launch fewer builders and tell the user what is loading the machine. If a builder's process tree runs at default niceness, `renice -n 19` + `ionice -c 3` it.
- **Parallelise only independent work**: never two agents on the same files or a tightly coupled change.
- **At most 3 concurrent build subagents per machine** (measured: 5 drove load 50–100 on 12 cores and manufactured false gate failures; more agents do not finish sooner). Queue the rest; launch the next when one reports.
- Reviewer subagents are read-only and cheap — they don't count toward the cap, but must not run gates.
- The orchestrator's own merged-tree re-verify counts as one of the gate slots.
- Tear down each worktree the moment its PR merges (repo teardown script if it has one), and stop any build daemons it left.

### What the orchestrator MUST do after a subagent reports (independent re-verification — never trust the summary)
- **Read the actual diff** (`rtk proxy git diff origin/<default>..HEAD`), not the agent's description. Review it adversarially for correctness and for the requirements above.
- **Confirm the pushed tip**: `git rev-parse HEAD` == `git rev-parse @{u}` in the worktree.
- **Re-run or spot-check the gate yourself** when feasible (at minimum confirm CI is green *for that exact tip*). A subagent that says "all green" with no pasted output = treat as not run.
- **Grep for leftover conflict markers**, confirm repo invariants (e.g. `alembic heads == 1`).
- Only then proceed to babysit (step 5) → final re-verify (step 6) → merge (step 7). Any gap the subagent skipped (e.g. no visual check), the orchestrator closes before merge.

If two requirements conflict or a subagent went off-spec, fix it in the worktree yourself and re-run the gate — do not merge an unverified claim.

### Cost discipline (measured 2026-10-01→08 on kyc; read before every wave)
Sonnet 5.5 workers were **84% of subagent tokens** (2.19B context tokens over 8,120 calls; median peak context **315k**, 30 of 42 agents over 200k). Cost ≈ calls × context, (prompt cache makes repeated context cheaper per token, but it still counts and still crowds the window), so the levers are context size and needless wake-ups, not model price.
- **Size the task, not just the model.** One PR = one reviewable concern in one subsystem. Split by platform (Android vs web vs backend) when a change spans more than one client tree or roughly 1,500 changed lines. Observed: a two-platform PR B needed four review rounds and agents at 400–580k.
- **Settle edge cases in every ruling.** When you rule on a design or a review finding, state the NULL/empty case, the lock mode and its conflicts, failure after an irreversible external effect, and the effect on approval rates. Observed: three Critical findings in one day came from rulings that omitted these (`FOR UPDATE` vs FK `KEY SHARE`; NULL retention date treated as "now"; a floor that blocked previously approvable sessions).
- **No idle waiting.** Workers run reviewers in the foreground, run the full gate as one background command reporting only `^VERIFY`, never Monitor/probe loops, and never spawn build sub-agents (the agent definitions enforce this, plus a `maxTurns` backstop). The orchestrator likewise waits on ONE completion notification per job (an `until`-loop), never periodic polls.
- **Hand off early.** Start a FRESH worker with a short handoff (done / remaining / traps / exact next command) instead of resuming one past ~150 tool calls; resuming a 400k agent for a 3-line fix costs more than briefing a new one.
- **Re-review the delta only.** After fixes, re-check `git diff <reviewed>..HEAD` against the specific findings and rulings, not the whole branch.
- **Orchestrator context is a cost too.** `/compact` after each merge wave; start a new session when the topic changes; persist state in claude-mem `work_state` first. Answer interim "still running" notifications in one line.
- **Cheapest correct tool first:** a direct command, then `haiku-scout`, then `sonnet-worker`, then `opus-worker`. Dispatch `haiku-scout` only when the lookup is bounded and offloading it saves more context than the dispatch costs: a known path needs no agent, and one exact search is just `rg`. Because it omits CLAUDE.md, its brief must carry any path exclusions or handling rules that apply.
- **API credits are not used by Claude Code.** The operator reserves the Max plan's monthly API credit for other work (decided 2026-10-08). Never route Claude Code work to API keys.
- **Quality baseline (2026-10-06→08, about 9 Opus-reviewed PRs):** nearly EVERY change came back "not ready" on its first Opus review, Opus-originated work included: three Critical/Important findings traced to the Opus orchestrator's own rulings. First-pass verdicts therefore measure the review bar and the domain risk, not the model. Measure instead: confirmed Critical/Important findings per comparable task, each attributed to its ORIGIN: builder defect (the spec covered it and the code violated it), orchestrator gap (the brief or ruling omitted or mis-decided it), or shared (underspecified, but a careful builder should have caught the risk). Also track correction effort, rounds to ready and post-merge escapes. A clean review does not prove reviewer recall. The sample is too small to separate Sonnet from Opus. Keep Opus review on behaviour changes, use `sonnet-reviewer` for routine diffs, and revisit routing only with attributed data from the next wave.
- **Measure after each wave:** `python3 ~/.claude/scripts/subagent-usage.py <project-dir> --since <date>`. Watch the Sonnet median peak context and the count over 200k; both should fall.

### Ownership and gates (2026-10-08)
- **Builders build; the orchestrator verifies.** A builder's brief ends at "built, scoped lanes green, committed, pushed, structured handoff". The orchestrator owns: the pre-implementation edge-case list in the brief, dispatching the INDEPENDENT reviewer (chosen by risk; never the builder's own), triaging findings, sending fixes back as a fresh or resumed builder brief, the full gate, CI and the merge. This replaces requirement 6's builder-dispatched review for new waves.
- **The full gate is SHA-pinned.** `verify.sh` prints the gated SHA. The merge candidate must equal it, or differ only by commits classified NON-EXECUTABLE: prose docs or ledger rows that no build, test, generator or agent instruction reads. These are NOT docs-only and require a re-gate: `CLAUDE.md`/`AGENTS.md`, generated specs, OpenAPI or SDK output, executable examples, CI and workflow files, anything a gate or test parses. Hosted CI must pass on the exact final tip either way. If main moved in a way that touches the PR's area, verify the merged result, not the old branch-local gate.
- **Delta re-review has a high-risk exception.** For security, data-lifecycle, concurrency or fusion changes, the re-check covers the delta AND the invariant it touches across the combined diff, not only the patch.
